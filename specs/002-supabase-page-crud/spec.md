# Feature Specification: 페이지 게시글 서버 저장 및 사용자별 접근 제어

**Feature Branch**: `002-supabase-page-crud`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "페이지 게시글 기능 구현할거야. 기존에 로컬스토리지로 구현돼있었으면 Supabase에 만든 page 테이블에 저장되도록 변경해줘. 내가 만든 db 테이블 구조는 변경하면 안돼. 로그인된 유저만 등록 가능하고 자신의 글만 조회, 수정, 삭제할 수 있어야돼."

## Clarifications

### Session 2026-07-16

- Q: page 테이블에 저장 항목이 없는 기존 글 속성(이모지 아이콘·커버 색상·최근
  수정 시각)은 어떻게 처리하는가? → A: UI에서 제거한다. 글은 제목·본문만
  편집하며, 목록 정렬과 시간 표시는 생성 시각 기준으로 한다.
- Q: 실제 로그인(인증) 전환이 이 기능 범위에 포함되는가? → A: 포함하지
  않는다. 실제 인증 전환은 별도 기능으로 진행하며, 이 기능은 로그인된 세션이
  존재한다는 전제 위에서 글 저장과 사용자별 접근 제어만 다룬다.
- Q: 서버에서 글 목록·내용을 불러오는 동안 화면에 무엇을 보여주는가? → A:
  목록 영역에 한국어 로딩 문구(예: "불러오는 중…")를 표시한다. 로딩 중에는
  빈 상태 문구가 노출되지 않아야 한다.
- Q: 편집 중 '저장됨' 표시는 언제 나타나는가? → A: 서버 저장이 실제로 성공한
  뒤에만 표시한다. 입력 즉시 뜨는 낙관적 표시는 사용하지 않으며, 저장 실패
  시에는 표시 대신 오류 안내를 보여준다.
- Q: page 테이블의 행 수준 보안 접근 규칙은 준비되어 있는가? → A: 확인 결과
  행 수준 보안은 켜져 있으나 정책이 없었다(2026-07-16, 계획 단계에서 발견).
  "본인 글만 조회·수정·삭제"를 강제하는 접근 정책 4개를 이 기능에서
  추가한다. 테이블 구조(컬럼·제약)는 변경하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 내 글이 계정에 저장되고 어디서든 유지됨 (Priority: P1)

로그인한 사용자가 새 글을 만들고 제목·본문을 편집하거나 글을 삭제하면, 그
결과가 브라우저가 아닌 사용자 계정 기준의 서버 저장소(사용자가 미리 만들어 둔
page 테이블)에 저장된다. 새로고침하거나, 로그아웃 후 다시 로그인하거나, 다른
브라우저·기기에서 접속해도 내 글 목록과 내용이 그대로 보인다.

**Why this priority**: 이 기능의 핵심 가치다. 글이 브라우저 로컬 저장소에만
있으면 브라우저를 바꾸거나 데이터가 지워질 때 글이 유실된다. 이 스토리 하나만
구현해도 "글이 계정에 안전하게 저장되는" 완결된 MVP가 된다.

**Independent Test**: 로그인 후 글을 생성·편집·삭제하고, 새로고침과
재로그인(또는 다른 브라우저 접속) 후에도 결과가 동일하게 유지되는지 확인하면
단독으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인된 사용자가 있을 때, **When** '＋ 새 글' 버튼 또는 '/page'
   명령으로 새 글을 만들고 제목과 본문을 입력하면, **Then** 글이 서버에
   저장되고 페이지를 새로고침해도 목록과 내용이 그대로 유지된다.
2. **Given** 글을 작성해 둔 계정이 있을 때, **When** 로그아웃 후 같은 계정으로
   다시 로그인하면, **Then** 이전에 작성한 글 목록과 내용이 그대로 보인다.
3. **Given** 글을 작성해 둔 계정이 있을 때, **When** 다른 브라우저나 기기에서
   같은 계정으로 로그인하면, **Then** 같은 글 목록과 내용이 보인다.
4. **Given** 글을 편집 중일 때, **When** 제목이나 본문을 변경하면, **Then**
   변경 내용이 서버에 저장되고, 저장이 성공한 뒤에 "저장됨" 표시가 나타난다.
5. **Given** 글이 여러 개 있을 때, **When** 글 하나를 삭제하면, **Then** 그
   글이 목록에서 사라지고 새로고침·재로그인 후에도 다시 나타나지 않는다.

---

### User Story 2 - 내 글만 보이고 내 글만 관리할 수 있음 (Priority: P2)

사용자에게는 자신이 작성한 글만 보인다. 다른 사용자가 작성한 글은 목록에
나타나지 않으며, 식별자를 알아내 직접 접근하는 등 어떤 경로로도 조회·수정·
삭제할 수 없다.

**Why this priority**: 여러 사용자가 하나의 저장소를 공유하므로 사용자 간
데이터 격리는 개인 기록 도구의 신뢰 기반이다. 저장 기능(US1)이 있어야 성립하는
속성이므로 P2로 두지만, 출시 전 반드시 함께 충족되어야 한다.

**Independent Test**: 계정 A로 글을 작성한 뒤 계정 B로 로그인해, B의 목록에
A의 글이 보이지 않고 A의 글 식별자로 조회·수정·삭제를 시도해도 모두 거부되는지
확인하면 단독으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 계정 A가 글을 작성해 두었을 때, **When** 계정 B로 로그인해 글
   목록을 열면, **Then** A의 글은 보이지 않고 B 자신의 글만 보인다.
2. **Given** 계정 A의 글 식별자를 계정 B가 알고 있을 때, **When** B가 그
   식별자로 글을 조회·수정·삭제하려 시도하면, **Then** 모두 거부되고 A의 글은
   변경되지 않는다.

---

### User Story 3 - 로그인하지 않으면 글을 쓸 수 없음 (Priority: P3)

로그인하지 않은 사용자는 글 목록·편집 화면에 접근할 수 없고 글을 등록할 수도
없다. 접근을 시도하면 로그인 화면으로 안내된다.

**Why this priority**: 글이 계정 단위로 저장되므로 소유자가 없는 글은 존재할
수 없다. 기존 앱에도 로그인 가드가 있어 흐름 자체는 유지되지만, 서버 저장
전환 후에도 이 규칙이 저장소 수준까지 일관되게 지켜져야 한다.

**Independent Test**: 로그아웃 상태에서 글 화면 접근과 글 등록을 시도해 모두
차단되고 로그인 화면으로 이동하는지 확인하면 단독으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인하지 않은 상태일 때, **When** 글 목록·편집 화면에 접근하면,
   **Then** 로그인 화면으로 이동한다.
2. **Given** 로그인하지 않은 상태일 때, **When** 어떤 경로로든 글 등록을
   시도하면, **Then** 등록이 거부되고 저장소에 글이 생성되지 않는다.

---

### Edge Cases

- 저장 실패(네트워크 오류 등): 한국어 안내를 표시하고, 사용자가 입력 중이던
  내용이 화면에서 즉시 사라지지 않아야 한다.
- 로그인 세션이 만료된 상태에서 편집·저장을 시도: 저장이 거부되고 로그인
  화면으로 안내된다.
- 다른 사용자의 글 식별자로 직접 조회·수정·삭제 시도: 모두 거부되며, 해당 글의
  존재 여부나 내용이 노출되지 않는다.
- 두 기기에서 같은 글을 동시에 편집: 마지막 저장이 우선하며(assumptions 참조)
  데이터가 손상되지 않는다.
- 제목을 비운 채 저장: 저장은 허용되고, 목록에는 기존과 같이 "제목 없음"으로
  표시된다.
- 글이 하나도 없는 계정으로 로그인: 기존 빈 상태 화면("아직 글이 없어요")이
  표시된다.
- 글을 불러오는 중: 빈 상태 문구가 아니라 로딩 문구가 표시된다. 로딩이 끝난
  뒤에야 목록 또는 빈 상태가 보인다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인된 사용자만 글을 등록(생성)할 수 있어야 한다. 비로그인
  상태의 등록 시도는 어떤 경로로든 거부되어야 한다.
- **FR-002**: 글의 생성·수정·삭제 결과는 사용자 계정 기준으로 서버 저장소에
  저장되어야 하며, 새로고침·재로그인·다른 브라우저나 기기에서의 접속 후에도
  유지되어야 한다.
- **FR-003**: 사용자는 자신이 작성한 글만 조회할 수 있어야 한다. 다른 사용자의
  글은 목록·상세 어디에도 나타나지 않아야 하며, 식별자를 통한 직접 접근도
  거부되어야 한다.
- **FR-004**: 사용자는 자신이 작성한 글만 수정·삭제할 수 있어야 한다. 타인의
  글에 대한 수정·삭제 시도는 거부되어야 한다.
- **FR-005**: 글 저장소는 사용자가 미리 만들어 둔 page 테이블(고유 식별자,
  생성 시각, 제목, 본문, 작성자 식별자)을 그대로 사용해야 하며, 테이블
  구조(컬럼·제약)를 변경하지 않아야 한다.
- **FR-006**: 글 데이터는 더 이상 브라우저 로컬 저장소에 보관하지 않는다.
  기존 로컬 저장 방식은 서버 저장으로 대체된다.
- **FR-007**: 저장·조회·삭제가 실패하면 한국어 안내를 표시해야 하며, 편집 중
  입력한 내용이 실패로 인해 즉시 유실되지 않아야 한다.
- **FR-008**: 기존 편집 흐름(목록 → 새 글 → 편집 → 자동 저장 → 삭제)과 한국어
  UI 문구는 유지되어야 한다.
- **FR-009**: 서버에 저장 항목이 없는 기존 글 속성(이모지 아이콘, 커버 색상,
  최근 수정 시각)은 UI에서 제거한다. 글은 제목과 본문만 편집하며, 글 목록의
  정렬과 목록·편집 화면의 시간 표시는 생성 시각 기준으로 한다.
- **FR-010**: 실제 로그인(인증) 전환은 별도 기능으로 진행되며 이 기능의 범위
  밖이다. 이 기능은 로그인된 세션이 존재한다는 전제 위에서 동작하며, 로그인된
  계정을 글의 작성자로 기록하고 접근 제어의 기준으로 사용하는 것까지를 범위로
  한다.
- **FR-011**: 서버에서 글 목록·내용을 불러오는 동안 목록 영역에 한국어 로딩
  문구(예: "불러오는 중…")를 표시해야 한다. 로딩이 끝나기 전에는 빈 상태
  문구("아직 글이 없어요")가 표시되지 않아야 한다. 문구·스타일의 세부는
  디자인 단계에서 `DESIGN.md` 기준으로 확정한다.
- **FR-012**: "저장됨" 표시는 서버 저장이 실제로 성공한 뒤에만 나타나야 한다.
  저장이 실패하면 "저장됨"을 표시하지 않고 FR-007의 오류 안내를 표시한다.

### Key Entities

- **글(페이지)**: 사용자가 작성하는 문서 단위. 고유 식별자, 제목(비울 수 있음),
  본문, 생성 시각을 가지며 정확히 한 명의 작성자(계정)에 속한다. 작성자만
  조회·수정·삭제할 수 있다.
- **사용자(계정)**: 로그인한 서비스 이용자. 자신이 작성한 글들의 소유자이며,
  글과 1:N 관계를 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 글을 작성·수정·삭제한 뒤 새로고침하거나 재로그인해도 결과가 100%
  유지된다(데이터 유실 0건).
- **SC-002**: 서로 다른 두 계정으로 각각 글을 작성했을 때, 상대방의 글이
  목록·상세·직접 접근 어디에서도 노출되는 사례가 0건이다.
- **SC-003**: 비로그인 상태에서 글을 등록할 수 있는 경로가 0개다.
- **SC-004**: 같은 계정으로 다른 브라우저·기기에서 로그인하면 동일한 글 목록과
  내용을 확인할 수 있다.
- **SC-005**: 일반적인 네트워크 환경에서 로그인 직후 글 목록이 3초 이내에
  표시된다.

## Assumptions

- 기존에 브라우저 로컬 저장소에 있던 글(프로토타입 시드 데이터 포함)은 서버로
  이관하지 않는다. 전환 후 사용자는 서버에 저장된 자신의 글만 보게 되며, 글이
  없는 계정은 빈 상태 화면에서 시작한다.
- 새 사용자를 위한 예시(시드) 글도 더 이상 자동 생성하지 않는다.
- 프로필(닉네임·아바타) 정보의 저장 방식 변경은 이 기능 범위 밖이다.
- 같은 글을 여러 곳에서 동시에 편집하는 경우 마지막 저장이 우선한다
  (last-write-wins). 별도의 충돌 병합 기능은 범위 밖이다.
- 입력 즉시 반영되는 기존 자동 저장 UX와 목록 검색 동작은 그대로 유지한다.
- 글 저장소(page 테이블)는 사용자가 미리 준비해 두었으며, 이 기능은 테이블
  구조(컬럼·제약)를 변경 없이 사용한다. 행 수준 보안 접근 정책은 확인 결과
  비어 있어, 사용자 승인에 따라 이 기능에서 추가한다(Clarifications 참조).
- 실제 인증(로그인) 기능은 별도 기능으로 제공된다. 계정 기반 저장의 완전한
  동작은 실제 인증이 먼저(또는 함께) 갖춰져야 확인할 수 있으므로, 이 기능은
  해당 기능에 의존한다.
- 이모지·커버 제거와 시간 표시 변경은 화면 변경을 수반하므로, 구현 시
  `DESIGN.md`의 해당 섹션을 같은 작업 단위로 갱신한다.
