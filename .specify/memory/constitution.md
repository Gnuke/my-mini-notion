# Nook Constitution

## Core Principles

### I. 테스트 우선 개발 — TDD (NON-NEGOTIABLE)

모든 프로덕션 코드는 superpowers 플러그인의 `/test-driven-development`
(`superpowers:test-driven-development` 스킬)가 정의한 TDD 절차를 의무적으로 따른다.
구현을 시작하는 세션마다 해당 스킬 문서를 먼저 읽고 그대로 적용한다.

- **Iron Law**: 실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다. 테스트보다
  먼저 작성된 코드는 삭제하고 테스트부터 다시 시작한다. "참고용으로 보관",
  "테스트 작성하며 변형" 모두 금지 — 삭제는 삭제다.
- **Red-Green-Refactor 사이클 엄수**:
  - RED: 하나의 동작만 검증하는, 이름이 명확한 최소 실패 테스트를 먼저 작성한다.
  - Verify RED (필수, 생략 불가): `npm test`를 실행해 테스트가 "기능 부재"라는
    올바른 이유로 실패하는 것을 직접 확인한다. 즉시 통과하면 기존 동작을 테스트한
    것이므로 테스트를 고치고, 에러(오타 등)로 실패하면 올바르게 실패할 때까지 고친다.
  - GREEN: 테스트를 통과시키는 최소한의 코드만 작성한다. 테스트가 요구하지 않는
    기능·옵션·리팩터링을 추가하지 않는다.
  - Verify GREEN (필수): 새 테스트와 기존 테스트가 모두 통과하고 출력이 무결
    (에러·경고 없음)함을 확인한다. 실패하면 테스트가 아니라 코드를 고친다.
  - REFACTOR: 통과 상태를 유지하며 중복 제거·이름 개선·헬퍼 추출만 수행한다.
    동작 추가 금지.
- **버그 수정도 동일**: 버그를 재현하는 실패 테스트를 먼저 작성한 뒤 수정한다.
  테스트 없는 버그 수정은 금지. 테스트가 수정을 증명하고 회귀를 방지한다.
- **모킹 규칙** (스킬의 `testing-anti-patterns.md`를 그대로 따른다):
  - 테스트는 실제 코드의 동작을 검증한다. 모의(mock) 객체의 존재나 동작을
    검증하는 테스트 금지.
  - 모킹은 불가피할 때만 최소한으로 사용한다. "안전하게 일단 모킹",
    "느릴 것 같으니 모킹"은 금지.
  - 모킹 전에 실제 메서드의 부수효과와 의존성 체인을 먼저 파악한다. 테스트가
    의존하는 부수효과를 가진 상위 메서드가 아니라, 실제로 느리거나 외부적인
    하위 연산만 모킹한다. 확신이 없으면 실제 구현으로 먼저 실행해 관찰한 뒤
    최소 지점에 모킹을 넣는다.
  - 모의 응답은 실제 API·데이터 구조 전체를 반영한다. 당장 쓰는 필드만 넣는
    부분 모킹 금지.
  - 테스트 전용 메서드를 프로덕션 클래스에 추가하지 않는다. 테스트 정리는
    테스트 유틸리티로 분리한다.
  - 모킹 설정이 테스트 로직보다 길어지면 설계를 의심하고, 실제 컴포넌트를 쓰는
    통합 테스트를 우선 고려한다.
- **예외**: 일회성 프로토타입, 자동 생성 코드, 설정 파일에 한하며, 반드시
  사용자의 사전 승인을 받는다. "이번 한 번만 건너뛰자"는 합리화이므로 중단한다.

근거: 테스트가 실패하는 것을 보지 못했다면 그 테스트가 올바른 것을 검증하는지
알 수 없다. 규칙의 문구를 어기는 것이 곧 규칙의 정신을 어기는 것이다.

### II. 디자인 명세 단일 출처 (DESIGN.md)

- 디자인 작업(스타일 값, UI 구조, 상태, UI 문자열 변경)을 시작하기 전에 반드시
  `DESIGN.md`를 Read 도구로 직접 읽는다. 기억이나 이전 대화 요약에 의존하지 않는다.
- 색상·크기 등 값이 필요하면 임의로 정하지 않고 `DESIGN.md`의 토큰과 리터럴
  값을 따른다. "미구현"/"미정" 항목은 지어내지 않고 사용자에게 확인한다.
- 코드와 `DESIGN.md`가 다른 부분을 발견하면 임의로 한쪽을 고치지 않는다.
  차이를 보고한 뒤 어느 쪽이 정답인지 확인받고 진행한다.

근거: 디자인 명세가 흩어지거나 어긋나면 UI 일관성이 깨진다. CLAUDE.md의 디자인
규칙을 헌법 수준으로 승격해 모든 spec-kit 산출물에도 적용한다.

### III. 한국어 UI

모든 사용자 노출 문자열(버튼 라벨, placeholder, 안내 문구, 빈 상태 메시지,
오류 메시지)은 한국어로 작성해야 한다(MUST). 코드 식별자, 주석, 커밋 메시지는
이 원칙의 적용 대상이 아니다.

근거: Nook은 UI 전체가 한국어인 제품이다. 부분적인 영어 노출은 제품 정체성을
해친다.

### IV. 단순성 (YAGNI)

- 현재 요구사항을 충족하는 가장 단순한 구현을 선택한다. 미래를 위한 옵션·
  추상화·설정값을 미리 만들지 않는다.
- 테스트를 통과시키는 데 필요한 것 이상을 구현하지 않는다(원칙 I의 GREEN 단계
  최소 구현과 동일한 기준).
- 불가피한 복잡성은 해당 기능 plan의 Complexity Tracking에 정당화를 기록해야
  한다.

근거: Nook은 "내가 실제로 쓰는 기능만 담은 가장 작은 노션"이다. 단순성은 제품
목표 그 자체다.

### V. 문서·코드 동기화

- 디자인을 변경했으면 같은 커밋 단위로 `DESIGN.md`의 해당 섹션을 갱신한다.
- 헌법·명세(spec)·계획(plan)·태스크(tasks) 문서가 코드와 어긋난 상태로 작업을
  끝내지 않는다.

근거: 어긋난 문서는 없는 문서보다 해롭다. 다음 작업자가 잘못된 전제로 시작하게
만든다.

## 기술 스택 및 테스트 환경

- **런타임/프레임워크**: Next.js 14 (App Router) + React 18 + TypeScript
  (strict). UI는 인라인 스타일과 `app/globals.css`의 CSS 변수 토큰을 사용한다.
- **테스트 프레임워크**: Vitest 4 + React Testing Library + jsdom
  (+ `@testing-library/jest-dom`, `@testing-library/user-event`).
  설정은 `vitest.config.ts`, 전역 셋업(jest-dom 매처, cleanup)은
  `vitest.setup.ts`.
- **테스트 실행**: `npm test`(1회 실행), `npm run test:watch`(감시 모드).
  원칙 I의 Verify RED / Verify GREEN 단계는 이 명령으로 수행한다.
- **테스트 위치**: 소스 파일 옆 콜로케이션(`lib/data.test.ts`처럼
  `*.test.ts` / `*.test.tsx`). 하네스 수준 검증은 `test/` 디렉터리에 둔다.
- **경로 별칭**: `@/*` (tsconfig paths; Vitest에서는 `resolve.tsconfigPaths`로
  해석).

## 개발 워크플로 및 품질 게이트

- **spec-kit 흐름**: `/speckit-specify` → (선택: `/speckit-clarify`) →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` 순서를 따른다.
- **태스크 규칙**: 모든 기능의 tasks.md에서 테스트 태스크는 필수이며, 대응하는
  구현 태스크보다 먼저 배치하고 먼저 수행한다(원칙 I).
- **완료 게이트**: 아래를 모두 만족해야 작업을 완료로 선언할 수 있다.
  - 새 함수·컴포넌트·동작마다 테스트가 존재하고, 각 테스트가 구현 전에
    예상한 이유로 실패하는 것을 확인했다.
  - `npm test` 전체 통과, 출력 무결(에러·경고 없음).
  - 테스트는 실제 코드를 사용한다(모킹은 불가피한 경우만).
  - 엣지 케이스와 오류 경로가 테스트로 덮여 있다.
  - 디자인 변경이 있었다면 `DESIGN.md`가 같은 작업 단위에서 갱신되었다.
- **리뷰**: 코드 리뷰는 위 게이트 충족 여부(특히 TDD 준수)를 검증한다.
  체크리스트를 모두 만족하지 못하면 TDD를 건너뛴 것이므로 삭제 후 다시 시작한다.

## Governance

- 이 헌법은 다른 모든 관행·지침보다 우선한다. `CLAUDE.md` 등 다른 지침과
  충돌하면 더 엄격한 쪽을 따르고 충돌을 사용자에게 보고한다.
- **개정 절차**: 개정은 사용자의 명시적 승인으로만 이루어진다. 개정 시 본
  문서의 버전과 날짜를 갱신하고, 상단 Sync Impact Report를 최신화하며, 의존
  템플릿(plan/spec/tasks)에 영향이 있으면 같은 작업 단위로 전파한다(원칙 V).
- **버전 정책 (semantic versioning)**: MAJOR = 원칙 제거·재정의 등 하위 호환
  파괴, MINOR = 원칙·섹션 추가 또는 실질적 확장, PATCH = 문구 명확화·오탈자
  수정 등 비의미적 정제.
- **준수 검토**: 모든 plan은 Constitution Check 게이트를 통과해야 하며, 위반은
  Complexity Tracking에 정당화 없이는 허용되지 않는다. 런타임 개발 지침은
  `CLAUDE.md`를 참조한다.
